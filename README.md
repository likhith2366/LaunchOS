# LaunchOS

A high-concurrency product launch platform in Swift 6: a hundred thousand people arrive
in the same ten seconds for a thousand units, and the system decides who gets in, in what
order, who gets inventory, and stays correct when things break.

Storing orders is not the problem. The problems are admitting people at a rate the
backend can actually survive, allocating scarce inventory without ever selling the same
unit twice, and keeping both correct when a request succeeds but its response is lost,
or a worker dies mid-checkout, or a customer abandons a reservation and the units have to
come back.

> **Status.** Everything described here is built, tested and measured. Every number in

> it, and is reproduced in full in [`results/RESULTS.md`](results/RESULTS.md) with the

## Why this is an engineering project and not a commerce backend

A commerce backend puts inventory in a row and updates it. That works until ten thousand
requests a second hit the same row, at which point Postgres serializes every one of them
behind a single lock and p99 collapses. Everything interesting here is what you do about
that: sharding the inventory, controlling admission so the backend never sees more load
than it can take, and defining fairness precisely enough to measure whether the queue is
actually fair.

Three claims, one of each kind:

- **A correctness claim** — zero oversold units under concurrent load, asserted after
  every committed transaction.
- **An optimization** — inventory sharding, with the speedup measured and the *next*
  bottleneck named rather than left as a ratio.
- **A controlled experiment** — an adaptive admission controller against a fixed-rate
  baseline on byte-identical traffic, including the case where the controller loses.

## The four engines

**1. Fair admission scheduler.** Customers join a queue, get a position, and are admitted
when capacity allows. Arrival order lives in Postgres, so it survives a restart and a
flushed Redis. A retry cannot improve a position — that falls out of the primary key, not
out of application logic. Admissions are released with jitter across the control interval
rather than in a batch at its boundary, because admitting 500 customers in the same
millisecond is a thundering herd of the system's own making.

**2. Concurrent inventory allocator.** Thousands of admitted customers compete for the
last few units. The invariant is `available + reserved + sold = total`, and it holds after
every committed transaction including expiry and cancellation. Units are split across
shards; a request probes a deterministic, customer-specific sequence of them.

**3. Fault-tolerant checkout coordinator.** A request succeeds and the response is lost.
The customer retries. They get the original order back, not a second one. A conditional
insert decides who owns an idempotency key, and the order commits in the same transaction
as the record a retry would read from — so there is no instant at which an order exists
that a retry cannot find.

**4. Launch traffic simulator.** Not an afterthought; it is where the numbers come from.
Bursty arrivals, retries, abandoned sessions, duplicate requests, think time. Seeded and
deterministic, so any failure replays exactly and two arms of an experiment see identical
traffic.

Plus **multi-node allocation**, because a single process that owns all allocation makes
for a thin distributed-systems claim. Both coordination strategies are implemented and
tested: Postgres as the arbiter (correct, contended) and lease-based shard ownership with
fence tokens (less contention, reclaim latency after a node death). The published numbers
below are from a single node, though — see the honest notes at the end.

## Reaching a million

The first version of this handled thousands. Getting to a million was not about making
any one operation faster — it was about removing operations whose cost grew with the
data:

| What | Was | Is |
| --- | --- | --- |
| Queue position | `count(*)` over everyone ahead — O(depth) | arithmetic on a dense arrival index and a departure counter — O(1) |
| Checkout commit | 6 round-trips (`BEGIN`, 3 writes, key update, `COMMIT`) | 1 statement |
| Shard probe | up to 4 round-trips, one per shard | 1, or 2 under contention |
| Admission check | a Postgres read per checkout | a Redis set lookup, falling through to Postgres on a miss |
| Invariant self-check | 2 O(table) scans every 5s | O(shards) every 5s, table scans every 2 minutes |
| Load generator | one task per customer | bounded worker pool, scripts derived from seed + index |

The details, and what each one cost to get right, are in
[`docs/ARCHITECTURE.md`](docs/ARCHITECTURE.md#what-it-takes-to-reach-a-million).

## The hot row

The obvious allocator is one row per SKU and a conditional update:

```sql
UPDATE inventory SET available = available - 1, reserved = reserved + 1
WHERE sku = 'LAUNCH-001' AND available > 0 RETURNING available;
```

That is correct. It is also a single row that every request in the system must take a
lock on, one at a time: the throughput ceiling is `1 / row-lock-hold-time` no matter how
many cores or connections you add.

The fix is to split the units across N rows and have each request pick one. The sequence
is `start + i·step (mod N)`, with both derived from a stable hash of the customer id and
`step` forced coprime to N so the sequence covers every shard exactly once and
terminates. Deterministic per customer, so a retry probes the same shards — otherwise a
retry could succeed where the first attempt failed purely by landing somewhere else.

And then sharding has a price, which is the interesting part. When twenty units remain
spread across sixty-four shards, a request that lands on empty shards fails even though
stock exists. Three mitigations, in increasing order of sophistication: probe a bounded
number of other shards, **collapse the shards back into one row** below a threshold, or
rebalance. LaunchOS does the first two; the measured effect of the collapse is reported
below, including the requests that still fail because the collapse is triggered *by* the
first failures.

## The adaptive admission controller

The differentiator, and a control problem rather than a database problem.

The baseline came first: a fixed-rate admitter, R customers per second, R set by hand. An
adaptive controller cannot be called better without a number to beat.

Then AIMD — additive increase, multiplicative decrease — driven by downstream health,
with three things that have to be right:

**The signal it controls on.** In-flight checkout count, not p99. p99 is laggy: by the
time it moves, admission has been too high for seconds and the controller is correcting a
problem it caused. In-flight count rises the moment service time increases. Control on the
leading indicator, alarm on the lagging one — both are tracked, and only one drives the
loop.

**Oscillation.** An EWMA on both signals plus a ±15% dead band in which the rate is not
touched. Without the dead band the controller reacts to every sample and the admission
graph is a sawtooth.

**The hard ceiling is not part of the control law.** An absolute cap on concurrent
checkout sessions, enforced whatever the loop concluded. The loop is feedback and can be
wrong; the ceiling is the thing that is not allowed to be. It is deliberately set out of
the way in the A/B experiment, because if the ceiling were what held p99 down then the
experiment would be measuring the ceiling and not AIMD.

**The thresholds are derived, not picked.** At a measured capacity of C checkouts per
second, holding p99 at a target T means holding in-flight work near `C × T` — Little's
Law, used forwards. An earlier run of this experiment left the in-flight threshold far
below anything the system could sit at; the controller backed off to its floor and
behaved exactly like the conservative fixed arm. That is a measurement of the tuning, not
of AIMD, and it is why the capacity is measured first and passed in.

## Fairness, defined

"Fairness policy" is not a metric. This is: **Spearman rank correlation between arrival
order and admission order.** Perfect FIFO is 1.0; a lottery over the whole waiting
population is near 0. Three policies are implemented and compared on it — strict FIFO,
lottery, and bucketed FIFO (ordered between time buckets, random within one).

Two things the measurement turned up that are worth more than the headline:

**A lottery is only as unfair as the arrival process lets it be.** Drawing at random from
everyone *currently waiting* looks almost like FIFO when customers trickle in, because the
pool you draw from only contains people who have already arrived. The policies separate
under a thundering herd, where the draw really is over the whole population. Both arrival
profiles are therefore reported, rather than whichever one flatters the result.

**Strict FIFO is a tunable, not a guarantee.** `seq` comes from a Postgres sequence and is
assigned at `INSERT`, but transactions commit in their own order. An admitter polling the
waiting set genuinely cannot see a lower-numbered entry that has not committed yet, so it
admits what it can see and arrival order and admission order end up crossed — with nobody
having retried or jumped the queue. Ordering on a pre-commit sequence number is not
sufficient for FIFO. Admitting only entries older than a **commit horizon** fixes it,
provided the horizon exceeds how long a join takes to commit under load.

That one is also the best argument for counting inversions instead of only correlating
ranks. In the run that first exposed it, 125 genuinely out-of-order admissions out of
2000 still scored a rank correlation of 0.99996 — reporting only the correlation would
have hidden it completely. The effect is load-dependent, so the sweep in the results
below may show none at a zero horizon; the horizon is justified by the mechanism and
sized by whichever runs do exhibit it.

## Failure handling

**Idempotency.** Every checkout carries a client-generated key.
`INSERT ... ON CONFLICT DO NOTHING RETURNING` is the conditional write that decides who
owns the work — exactly one concurrent caller gets a row back. The order id is generated
before the transaction so the response body can be committed *with* the order. A retry
arriving while the original is still running blocks briefly and then gets a 409: blocking
absorbs the common case, and either answer is acceptable where a duplicate order is not.

**The crash window.** Between reserving inventory and recording the order, a worker death
leaves a unit reserved with no order to complete it. Three things close it: the shared
commit above, release of in-flight keys whose owner is gone (so a customer is not locked
out of their own order), and reservation expiry as the backstop. A node's reservations can
also be reclaimed early once it stops heartbeating, which turns a 90-second TTL into a few
seconds — expiry is what makes that an optimization rather than a requirement.

**Expiry at scale.** Scanning the reservation table for expired rows does not survive
contact with a hundred thousand reservations. Reservations are bucketed by expiry minute
with a partial index, swept in bounded batches, one transaction per reservation — because
reclaim has to be independently retryable, and a batch-wide transaction means one
contended row stalls the reclaim of every other unit in the batch.

**Durable queue order.** Postgres holds it; Redis caches positions and is never
authoritative. Killing Redis mid-launch costs latency, not order.

**Continuous self-check.** The running node verifies the inventory invariant on a timer
and exports the result. Tests and the simulator only check when someone runs them, and a
launch is a one-shot event: a unit sold twice at 09:00:03 has no second chance to be
noticed. The self-check never repairs anything, because a silent repair destroys the
evidence.

## Stack

| Layer | Choice | Why |
|---|---|---|
| Language | Swift 6, strict concurrency | Actors give compiler-enforced isolation where isolation is wanted — and deliberately are *not* used on the allocation path, where an actor would reintroduce the global lock sharding exists to remove. |
| Web | Vapor on SwiftNIO | Mature, async, and what Apple used for Password Monitoring. |
| Durable state | PostgreSQL 16 | Inventory, reservations, orders, idempotency keys, queue log. Source of truth. Every invariant is a conditional update or a transaction. |
| Coordination | Redis | Queue positions, in-flight counters, node heartbeats. Fast, and explicitly not authoritative. |
| Observability | Prometheus and Grafana | Hand-rolled exposition, so the format is visible and there is no client library to keep in step. |
| Load and faults | Swift CLI | Seeded, deterministic, replayable. |
| Dashboard | React, TypeScript | Operator view. Read-only by design: a dashboard that can change a launch in progress can ruin one by a misclick. |
| Runtime | Docker Compose | Three allocator nodes, Postgres, Redis, Prometheus, Grafana, all local. |

### Natively in WSL2 — how these numbers were produced

Vapor targets Linux and macOS, so the build runs in WSL2, in a WSL-local directory
rather than over `/mnt/...`: SwiftPM does a very large amount of small-file and git IO,
and over the Windows drive mount a dependency resolve that takes seconds natively takes
many minutes.

```bash
scripts/wsl-deps.sh               # Swift toolchain + two system libraries, no root needed
scripts/wsl-build.sh -c release
scripts/wsl-services.sh start     # Postgres and Redis, unpacked under ~/.local, no root
scripts/wsl-cluster.sh start      # allocator node(s)
scripts/run-experiments.sh        # the whole suite, writing results/
```

`scripts/wsl-services.sh` exists because Docker Desktop on Windows is a single point of
failure for the entire inner loop, and a measurement run should not be blocked on it. It
brings up Postgres and Redis from unpacked `.deb` files under `~/.local` as the ordinary
user. (Postgres refuses to run as root anyway.)

## Honest notes

Kept because the project is not worth much without them.

- **A hundred thousand simulated customers is not a hundred thousand simultaneous TCP
  connections**, and claiming otherwise on a laptop would not survive questioning. Every
  result reports offered arrival rate, peak concurrent connections and completed
  purchases as three separate numbers.
- **Where the controller loses.** Under a steady load inside capacity, a fixed rate tuned
  to that load beats it, because the controller is still probing upward and backing off.
  The experiment includes a fixed arm set *exactly* at measured capacity — the strongest
  possible fixed baseline — and reports the comparison whichever way it came out. The
  controller's claim is not that it beats a perfectly tuned fixed rate on a load that
  never changes; it is that it finds a workable rate without being told one.
- **What sharding cost.** Tail fragmentation, measured, with the mitigation's residual
  failures reported rather than rounded to zero.
- **Docker Compose is written and validated (`docker compose config`) but the published
  numbers were produced by the WSL path**, because Docker Desktop was unavailable on the
  machine during the measurement runs. The Compose stack has not been executed
  end-to-end.
- **Four bugs found while building this**, all written up in `docs/DECISIONS.md`: shard
  collapse losing every available unit (a data-modifying CTE whose second half silently
  did not run), the Redis position cache saving nothing (the expensive query ran before
  the cache was consulted), and the bucketed expiry sweep ignoring its launch filter.
  The first was caught by the invariant, the second by an experiment behaving
  nonsensically, the third by three failing tests. The fourth — a single-pass Redis
  `SCAN` treated as a query, which made node-liveness detection return nothing and could
  have made crash recovery reclaim a live node's reservations — was found by inspection,
  and is the one the measurements would not have caught.
- **The published numbers are from a single allocator node.** Multi-node allocation is
  implemented in both modes and covered by integration tests — three allocators against
  one sharded launch without overselling, lease takeover issuing a new fence token, a
  dead node's reservations being identifiable — but the measurement suite ran against one
  node. So the result the spec asked for here, *"lease-based shard ownership removed N%
  of database contention at the cost of M seconds of reclaim latency"*, is **not
  measured**. The machinery to measure it exists (`NODES=3 scripts/run-experiments.sh`,
  `MULTI_NODE_MODE=leasedShards`); the number does not, and it would be dishonest to
  quote one.
- **"A million" means a million customers through the allocator, and a million-deep
  queue — not a million concurrent connections.** The load generator runs a bounded
  worker pool, so it offers load at a rate the machine can sustain rather than opening a
  million sockets. It reports **arrival lag** for exactly this reason: if the generator
  fell behind its own schedule, the offered arrival rate is the rate that was asked for
  rather than the rate delivered, and the run is partly measuring its own harness.
- **The queue-depth measurement seeds rows in bulk rather than joining over HTTP.** Depth
  is the independent variable there; how long a million HTTP joins take is a different
  question, and the throughput runs answer that one.
- **The position estimate can be wrong, and by how much is measured, not assumed.** Index
  gaps from rolled-back joins make it read high; out-of-order departures under a lottery
  policy make it read high at the back of the queue and low at the front.
  `?position=exact` always answers from the count, which is how the error stays a number.
  It measured zero at every depth tested, which is the dense per-launch arrival sequence
  working — deriving the index from the globally shared sequence drifted without bound.
- **The biggest scale bug in here was this project's own monitoring.** Continuous
  invariant verification ran two O(table) queries every five seconds, so as a launch grew
  the checker read more and more and throughput fell from 814 allocations/s to about 70.
  The lesson generalises past this codebase: verification that scales with the data will
  eventually cost more than the work it is checking, and the cheap half of a check is
  usually the half that catches the bug.
- **Single machine, single Postgres.** Every number is from one 8-core WSL2 host with the
  database, Redis, the allocator node and the load generator all on it, competing for the
  same eight cores. The shapes are real; the absolute figures are a laptop's.
